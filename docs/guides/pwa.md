# Progressive Web App

OpenCouncil installs as an app from the browser. This guide describes the parts that make that work and the rules they follow.

## Concept

A Progressive Web App (PWA) is the normal website plus three things:

- A **web app manifest** that names the app, lists its icons and asks the browser to open it without browser chrome.
- A **service worker** that the browser runs in the background. Ours caches static assets and serves an offline page.
- **HTTPS**, which the site already has.

An installed app opens from the home screen in its own window. It is the same site on the same URL. There is no app-store build.

## Parts

| Part | File | Role |
|------|------|------|
| Manifest | `src/app/manifest.ts` | Served at `/manifest.webmanifest`. Dynamic per realm, like `robots.ts`. |
| Icons | `public/icons/` | Generated by `npm run generate-pwa-icons` from `public/logo.png`. |
| iOS metadata | `src/app/layout.tsx` | `appleWebApp` and the apple touch icon. iOS ignores the manifest for these. |
| Service worker | `public/sw.js` | Plain JavaScript, no build step. |
| Registration | `src/components/pwa/ServiceWorkerRegistration.tsx` | Registers the worker on production builds only. |
| Offline page | `src/app/[locale]/(bare)/offline/page.tsx` | Shown when a navigation fails without a network. |
| Install prompt | `src/components/pwa/InstallPrompt.tsx` | Asks the visitor to install. Rules in `src/lib/pwa/installPrompt.ts`. |
| Strings | `messages/*/pwa.json` | Manifest description, prompt copy, offline page copy. |

## Manifest

The manifest is a metadata route. It reads the realm from the request host, so `opencouncil.fr` gets a French description and `lang`. The `start_url` is relative, so the installed app opens on the domain it was installed from. The `id` is `/`, so a later change to `start_url` does not create a second app.

`start_url` carries `?utm_source=pwa`. Analytics can then count launches from the home screen.

## Service worker

The worker handles same-origin `GET` requests only. The rules, in order:

1. A navigation goes to the network. When the network fails, the worker serves the offline page of the request locale.
2. A build asset under `/_next/static/` is cache-first. The URL contains the content hash, so a cached copy is never stale.
3. Requests under `/_next/`, `/api/` and `/ingest/` pass through untouched.
4. An image or a font from `public/` is stale-while-revalidate.

The worker never caches an HTML page. Pages vary by the signed-in user, and `next.config.mjs` marks them `private, no-store` for the same reason. The offline pages are the one exception. They render no per-user data.

At install, the worker fetches the offline page of every locale, and the build assets that the page references. The worker then calls `skipWaiting`, and takes over open pages at activation. Old caches carry a version number in their name. Bump `VERSION` in `public/sw.js` when the caching rules change. Activation deletes the caches of older versions.

The test `src/lib/pwa/__tests__/sw.test.ts` runs the worker in a sandbox with a fake Cache Storage. It also guards the locale prefix list in the worker against `src/i18n/config.ts`.

`next.config.mjs` serves `/sw.js` with `Cache-Control: no-cache`. The browser then sees a new worker on the first navigation after a deploy.

## Install prompt

The prompt opens 1.5 seconds after a page load. On a phone it is a bottom sheet over the dimmed page. On a desktop it is a card in the bottom-right corner, and the page behind it stays usable. The copy is one headline and one line; no list of benefits.

What the prompt shows depends on the browser:

- **Chromium on Android or desktop** fires `beforeinstallprompt`. The prompt shows an Install button that replays that event.
- **iOS** has no such event. The prompt shows the share-sheet steps.
- **Other Android browsers** get the browser-menu steps. When the event arrives later, the prompt switches to the Install button.
- **A desktop browser without the event** never sees the prompt.

The prompt stays hidden when:

- the page already runs as the installed app (`display-mode: standalone`, or `navigator.standalone` on iOS);
- the app was installed from this browser (`oc-app-installed` in `localStorage`);
- the visitor chose "Not now" less than seven days ago (`oc-install-prompt-dismissed` holds the time);
- the path is an embed, the presentation view or a share page (`INSTALL_PROMPT_EXCLUDED_PATH`).

The prompt captures `install_prompt_shown`, `install_prompt_dismissed`, `install_prompt_answered` (with the browser's `outcome`) and `app_installed` through `captureEvent`.

## Testing a change

Preview deployments run production builds, so the worker registers on `pr-N.opencouncil.dev`. Chrome DevTools, Application tab, shows the manifest, the worker and the caches. The "Offline" checkbox there exercises the offline page.

The worker does not register on `npm run dev`. A worker from an earlier production build on the same origin can still be active. Unregister it from the Application tab when a change does not show up.

## Not in scope

- **App stores.** Google Play accepts a PWA wrapped as a Trusted Web Activity. Apple rejects a plain wrapper and needs a native shell. Both are separate projects.
- **Web push.** Notifications go out by email, WhatsApp and SMS (see `docs/notifications.prd.md`). The worker has no push handler.
- **Offline content.** Only the offline page and static assets are cached. Meeting pages need a network.
